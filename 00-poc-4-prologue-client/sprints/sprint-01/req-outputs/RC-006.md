## User Story
As a General Ledger accountant,
I want to see the current status of a journal entry along with who edited or posted it and when,
So that I can track the audit trail and lifecycle of financial transactions.

## Functional Requirements
1. Each journal entry must have a Status field that reflects its current lifecycle state.
2. The minimum required status values are: "Unposted" (entry created, not yet posted) and "Posted" (entry has been posted to the ledger).
3. Status must be displayed prominently in the journal entry header.
4. The system must record and display Edit Date/Time — the timestamp of the most recent save of the entry.
5. The system must record and display Edit User ID — the identifier of the user who performed the most recent save.
6. Edit Date/Time and Edit User ID must be automatically updated by the system on every save — they must not be user-editable.
7. The system must record and display Posted Date/Time — the timestamp when the entry was posted. This field must be empty for Unposted entries.
8. The system must record and display Poster User ID — the identifier of the user who posted the entry. This field must be empty for Unposted entries — population rule pending OQ-002 resolution.
9. All audit trail fields (Edit Date/Time, Edit User ID, Posted Date/Time, Poster User ID) must be read-only — users must not be able to modify them.

## Acceptance Criteria
1. Given a journal entry is in "Unposted" status, when the header is displayed, then the Status field shows "Unposted".
2. Given a journal entry has been posted, when the header is displayed, then the Status field shows "Posted".
3. Given the user saves an entry, when the save completes, then Edit Date/Time is updated to the current server timestamp.
4. Given the user saves an entry, when the save completes, then Edit User ID is updated to reflect the authenticated user's identifier.
5. Given an entry has not been posted, when the header is displayed, then Posted Date/Time is empty.
6. Given an entry has not been posted, when the header is displayed, then Poster User ID is empty — pending OQ-002 resolution.
7. Given an entry has been posted, when the header is displayed, then Posted Date/Time shows the timestamp of posting and Poster User ID shows the posting user's identifier.
8. Given the user attempts to edit any audit trail field (Edit Date/Time, Edit User ID, Posted Date/Time, Poster User ID), then the field is not editable — it displays as read-only.

## Non-Functional Requirements
| Category      | Requirement                                                              |
|---------------|--------------------------------------------------------------------------|
| Performance   | Audit fields must load as part of the journal entry header — no separate request. |
| Security      | Audit fields must be immutable — no API endpoint may accept user-provided values for these fields. |
| Accessibility | Status must be communicated to screen readers as a labelled field, not only as visual colour. |
| Usability     | Status must be visually prominent in the header layout.                  |
| Other         | No additional non-functional requirements identified in source.          |

## UI Components Affected
- Status display component in header
- Read-only audit field components (Edit Date/Time, Edit User ID, Posted Date/Time, Poster User ID)

## BFF Endpoints Needed
- Audit fields are included in the response of GET /journal-entries/{journalId} (covered by RC-002)
- Status transitions are managed server-side; no separate status endpoint needed unless posting is a dedicated action (posting mechanism pending OQ-009 resolution)

## Intra-sprint Dependencies
- Depends on: RC-002 — audit fields are part of the header display
- Depends on: RC-003 — edits trigger audit field updates
