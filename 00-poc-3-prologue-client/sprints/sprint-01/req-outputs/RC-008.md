## User Story
As a GL supervisor,
I want journal entries to be routable through a configurable approval workflow before they can be posted,
So that entries are reviewed and approved by the appropriate authorised personnel in accordance with segregation-of-duties controls.

## Functional Requirements
1. The journal entry header must include a Routing field that identifies the routing rule or approver for the entry.
2. The system must support a configurable Journal Entry Routing Process where routing rules determine which entries require approval and by whom.
3. A journal entry in routing/approval state must display its routing status visibly in the header.
4. Approvers must be able to approve or reject a journal entry from a dedicated routing/approval view.
5. A rejected entry must return to the originator with the rejection reason visible.
6. Only an approved (or routing-exempt) journal entry may be posted -- see RC-004.
7. The routing configuration must be administrable through a separate GL Control / Administration module accessible from the Journal Entry Routing Process navigation item.
8. The system must support a bypass mode for entries that do not require approval routing (e.g. system-generated auto-reversals).

## Acceptance Criteria
1. Given a journal entry with a Routing value set, when the entry is saved, then its status reflects that it is awaiting routing approval.
2. Given an approver opens their approval queue, when a journal entry is pending their approval, then they can view the full entry, approve it, or reject it with a mandatory rejection reason.
3. Given an approver rejects an entry, when the rejection is submitted, then the originator is notified and the entry returns to "Unposted" status with the rejection reason visible.
4. Given an approved entry, when a user with post permission clicks Post, then posting proceeds (subject to balance validation in RC-003 and period control in RC-015).
5. Given a journal entry with no Routing value, when the entry is saved, then no approval is required and it can be posted directly (if permitted by configuration).

## Non-Functional Requirements
| Category      | Requirement                                                                   |
|---------------|-------------------------------------------------------------------------------|
| Performance   | Routing queue must load within 3 seconds.                                     |
| Security      | Only designated approvers may approve/reject entries in their routing queue.  |
| Accessibility | Approval actions must be accessible via keyboard.                             |
| Usability     | The current routing/approval status must be visible on the entry at all times.|
| Other         | Routing configuration model detail is pending confirmation; see Open Question OQ-022. |

## UI Components Affected
- Routing field (text input or dropdown in header)
- Routing status indicator (header)
- Approval queue view (separate screen / panel)
- Approve / Reject action buttons (in approval queue)
- Rejection reason input
- GL Control / Routing Administration screen

## BFF Endpoints Needed
- GET /routing-rules -- list routing rule configurations
- POST /journal-entries/{id}/submit-for-approval -- submit entry to routing
- POST /journal-entries/{id}/approve -- approve an entry
- POST /journal-entries/{id}/reject -- reject an entry with reason
- GET /journal-entries?pendingApproval=true&approverId={id} -- approval queue
